# Native Nimiq Pay HTLC payouts

The campaign organiser's local wallet **authorises** a reward. The active Nimiq Pay remote HTLC **funds** it. These are different addresses. `payment-ready` remains an approval, and only independently verified, finalized successful execution is paid.

Spending remains off by default. Mainnet is explicitly blocked in the payment service, regardless of configuration. Mobile-test and PostgreSQL staging retain their independent financial-route barriers. This change does not deploy anything or change environment variables.

The SQLite entry point refuses Render/staging/PostgreSQL environment markers. The existing PostgreSQL Render + Neon deployment is not a testnet payout deployment; supporting payouts there requires a separate reviewed implementation. No deployment path currently has release approval to spend, and no environment values were changed for this review.

`PaymentGate.senderBindingSupported` means an **atomic wallet commitment to the reserved sender through native confirmation**. It is `false` on both runtimes because the SDK provides no such guarantee. The separate `htlcVerificationSupported` field describes independent server HTLC funding/receipt verification: `true` on SQLite, `false` on PostgreSQL staging. Neither capability flag authorizes spending. `enabled` continues to reflect the server configuration and network gates; it does not certify host freshness, physical validation or release readiness. The UI uses HTLC verification support when presenting the candidate funding address.

## Wallet and authorisation

The reviewed [native host](https://github.com/nimiq/nimiq-pay-app/blob/dd90a9c5443be3f4e0ddeac454486c9d512fcae3/src/composables/useMiniAppHost.ts) was inspected at revision `dd90a9c5443be3f4e0ddeac454486c9d512fcae3` (`getNimiqAccounts`, `listAccounts` and `sign`). It returns the local wallet followed by its active remote HTLC. This is a host-specific interpretation, not an SDK ordering contract or a guarantee about the installed phone binary. `provider.sign()` uses the local key. The account list identifies accounts; it never proves ownership. Contributors and organiser wallet binding still use the existing cryptographically verified message-signature protocol.

Payout preparation requires exactly both accounts and compares the local address with the campaign's immutable, authenticated organiser wallet. A missing HTLC blocks payment. The browser submits the HTLC address as an untrusted lookup candidate to the payment challenge endpoint. The server independently calls `getAccountByAddress` through its configured read-only RPC and checks:

- Correct network and established consensus.
- The returned address equals the requested address and its account type is `htlc`.
- Its sender equals the campaign's signed organiser wallet.
- Its recipient is a trusted Nimiq Pay cosigner for this network.
- Its balance covers the reward plus the exact fee, using safe integer Luna arithmetic.
- Its timeout is later than the server clock. Albatross timeout values are Unix milliseconds, not heights; synchronised server time is required.

Trust roots are derived with Nimiq core from the [official public keys](https://github.com/nimiq/nimiq-pay-app/blob/dd90a9c5443be3f4e0ddeac454486c9d512fcae3/src/lib/index.ts), reviewed on 2026-11-10. Testnet has two keys; mainnet has one separate key. No browser or environment setting can extend these lists. A key rotation requires code/source review.

The session-bound signed payment challenge includes the HTLC transaction sender, organiser authoriser, HTLC cosigner recipient and timeout, contributor recipient, reward, fee, network, campaign, claim, expiry and random nonce. The backend requires the signature to derive the campaign organiser's local wallet. It independently verifies the HTLC again at reservation and compares all bound details. Knowing or listing either address cannot substitute for this signature.

## Reservation and native request

After asynchronous checks, the server rechecks immutable campaign/claim details, session, expiry, unused challenge, allocation and existing attempts inside the database transaction. It freezes the HTLC address as `intent.sender`, reserves exactly one durable attempt, consumes the nonce and returns a random permit whose hash is stored. Concurrent requests cannot reserve twice.

Dispatch atomically consumes that permit once. Lost reservation or dispatch acknowledgements stop the browser. A reservation stays locked across restarts, cancellations, errors, timeouts and failed execution. There is no payment reset or retry API.

The browser calls the documented `disconnect()` before critical `listAccounts()` reads: connection, payout preparation, the pre-signature check, before reservation and immediately before the native call after dispatch acknowledgement. SDK 0.2.5 caches successful lists; another `listAccounts()` alone cannot refresh them. Disconnect clears the provider cache and emits a local event; it does not revoke host permissions or end the backend session. Renewed account access can open another approval dialog. Rejection, disconnect failure or read failure stops the flow without using an older approval. Before reservation this creates no attempt; after reservation it records cancellation/error as uncertain and never releases the attempt.

Both accounts must still match the reviewed pair, and the host network is rechecked after the asynchronous pre-reservation and pre-native reads. A changed local wallet or HTLC blocks the native call. A per-provider/claim browser guard rejects concurrent submissions and remains locked once reservation is requested, even if its response is lost; the durable server lock protects reloads and other clients.

The only native request is `provider.sendBasicTransaction({recipient, value, fee})`. There is no sender parameter. The [official transaction builder](https://github.com/nimiq/nimiq-pay-app/blob/dd90a9c5443be3f4e0ddeac454486c9d512fcae3/src/lib/tx.ts) uses the active remote address with HTLC sender type, Basic recipient type and an early-resolve proof. It chooses `max(remoteHeight, networkHeight) + 1` internally. NimClaim does not send a validity-start height or assume the host honours one.

A native timeout does not dismiss a wallet prompt. Late approval may still broadcast. Browser-reported hashes, cancellations and errors are hints only, and never prove success or non-broadcast. Every ambiguous outcome stays UNKNOWN and must be reconciled without another wallet request.

## Independent verification

`server/rpc.ts` accepts only `getAccountByAddress`, `getNetworkId`, `isConsensusEstablished`, `getBlockNumber`, `getTransactionByHash`, `getBlockByNumber` and `getMacroBlockAfter`. It requires official `result.data` envelopes, matching IDs, bounded responses/timeouts and no redirects. Browser input cannot select RPC URLs or credentials; write methods are rejected before transport.

Reconciliation verifies the exact hash, HTLC sender type (2), Basic recipient type (0), addresses, reward, fee and network; zero flags; and empty sender/recipient data. The installed `@nimiq/core` **2.23.0** was executed locally against structurally serialized early- and timeout-resolve proof bytes. `HashedTimeLockedContract.proofToPlain()` returns an object with `type: "early-resolve"`, `raw`, `signer`, `signature`, `publicKey`, `pathLength`, `creator`, `creatorSignature`, `creatorPublicKey` and `creatorPathLength`. Timeout resolve returns `type: "timeout-resolve"` and the creator fields. `tests/rpc.test.ts` asserts those complete runtime objects using the actual WASM-backed package, with no parser mock. Synthetic signatures establish decoder shape only; they are not cryptographic payment evidence. The existing `proof.type === "early-resolve"` detection is correct and unchanged.

Reconciliation decodes the raw sender proof using Nimiq core and requires early resolve, the campaign organiser as creator, a network-trusted cosigner public key and the corresponding single-signature identities. Missing, malformed, wrong-mode and wrong-identity proofs cannot confirm a payment.

The historical `validity_start_height` database column stores the **minimum acceptable inclusion block** recorded at reservation. It is not the requested or expected native transaction validity height. Inclusion before that minimum is rejected. The actual transaction validity start must not exceed inclusion, and must remain consistent across the independent reads. Old Basic-sender attempts are not silently converted to HTLC payments and remain locked if they cannot satisfy verification.

The transaction must appear in the canonical micro block, with matching explicit execution result. The following macro block must be available at or below the verified head, on the same network, with a nonempty justification. A second inclusion-block read must retain the canonical hash and transaction evidence. Hash consumption is globally unique across claims. Numerical confirmations or a browser hash alone never produce a paid receipt.

Finalized successful execution becomes CONFIRMED. Finalized execution failure becomes FAILED with an unpaid-reward receipt. Unavailable, malformed, changed or insufficient finality evidence stays UNKNOWN. Known transaction/proof mismatches are rejected. Reconciliation remains possible after campaign expiry.

## Verification limits and release blockers

The configured full/history RPC node is the trust boundary for account state, signature validity, execution and finality. NimClaim decodes and checks proof identities, but does not independently re-execute the HTLC, cryptographically validate both transaction signatures, or verify validator/macro signatures as a light client. Automated RPC fixtures contain explicitly synthetic proofs and finality evidence; they are not real cosigner signatures or successful payment evidence.

The [provider contract](https://nimiq.dev/mini-apps/api-reference/nimiq-provider#disconnect) does not guarantee account ordering or an atomic native read. The installed SDK 0.2.5 implementation clears its internal addresses with `disconnect()` and delegates the next `listAccounts()` request to its adapter. This fixes the application's reliance on repeated cached SDK reads.

The exact reviewed [host bridge](https://github.com/nimiq/nimiq-pay-app/blob/dd90a9c5443be3f4e0ddeac454486c9d512fcae3/web3-provider/src/provider.ts) has a **second cache** in [session storage](https://github.com/nimiq/nimiq-pay-app/blob/dd90a9c5443be3f4e0ddeac454486c9d512fcae3/web3-provider/src/account-cache.ts). Its `fetchAccounts` can return that approved list without invoking the native confirmation handler; no bridge-cache clearing on provider disconnect was found in this revision. Host pushes update the caches, but `pushNimiqAccounts` deliberately retains the old list while a replacement remote address is unavailable. Consequently, clearing the SDK cache does not prove a fresh native read or renewed native approval on this host. The caching test double models the documented SDK cache, not proof of bridge/device behavior. Current upstream `main` was rechecked at **`df61e2cf51ff480ab501fc4e09bba2a7241dd48b`** (commit dated 2026-11-10). Its [provider bridge](https://github.com/nimiq/nimiq-pay-app/blob/df61e2cf51ff480ab501fc4e09bba2a7241dd48b/web3-provider/src/provider.ts#L109-L148) and [account handler](https://github.com/nimiq/nimiq-pay-app/blob/df61e2cf51ff480ab501fc4e09bba2a7241dd48b/src/composables/useMiniAppHost.ts#L1516-L1558) are unchanged from the previously reviewed revision; its [session cache](https://github.com/nimiq/nimiq-pay-app/blob/df61e2cf51ff480ab501fc4e09bba2a7241dd48b/web3-provider/src/account-cache.ts) also has no invalidation method. This host cannot guarantee a fresh HTLC address to the Mini App. A deterministic two-cache characterization test demonstrates why SDK disconnect alone is insufficient, without using a real wallet. Resolving this needs a reviewed host capability/change and physical cache/replacement validation; it remains a spending release blocker.

The API also provides no atomic sender commitment spanning the native confirmation prompt. A switch after the last check can produce a different transaction; independent verification rejects it, but cannot undo a broadcast. Supported host versions, lock/background, late approval and physical testnet behavior still require owner-operated validation.

No physical wallet, live payment or live RPC evidence is asserted by automated tests. Keep spending disabled until the required integration checks pass and review is complete. Mainnet remains NO-GO; PostgreSQL staging has no broadcast implementation. Existing schema v2 immutability, unique-attempt/hash constraints, credentials, sessions, claim signatures and replay protections are retained.
