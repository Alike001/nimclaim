# Security and API contract

NimClaim is deployed as a MAINNET Mini App, not an audited payments service. Organiser access and contributor claims use Nimiq Pay wallet signatures. Organisers send NIM separately through Nimiq Pay; the hosted MAINNET runtime can independently verify an exact finalized transfer by hash. Native spending, escrow and automatic payout remain disabled.

## Boundaries

- Setup generates 256-bit random organiser credentials; passwords are salted and hashed with scrypt. Login issues a 256-bit random HttpOnly, SameSite=Strict session cookie with an eight-hour absolute expiry; only its SHA-256 hash is stored. HTTPS also sets Secure. Logout revokes the session (SQLite deletes it; PostgreSQL expires it without DELETE). Sessions survive server restarts and expire server-side.
- Every POST requires the exact configured Origin and JSON content type; request bodies are capped at 16 KiB. Zod validates strict input shapes and rejects extra signer/address fields. Administrative APIs require a valid session. Public claim APIs require a 256-bit invitation token. There is no CORS allowance.
- No third-party frontend resources or analytics. Production CSP restricts resources to the app's origin. Responses are no-store and no-referrer; links carry tokens in fragments. Application error logs do not contain request bodies. Infrastructure must also avoid logging bodies, cookies and signatures.
- Local SQLite development uses process-local IP rate limits: 10 login requests/minute; 180 other API requests/minute. No forwarded IP headers are trusted. Behind a reverse proxy these SQLite limits are shared by all users; durable per-client limiting and carefully configured proxy trust are required for a public deployment. The active MAINNET PostgreSQL runtime uses shared database-backed minute buckets, but these are deployment-wide rather than full per-client quotas; edge abuse controls remain an operational follow-up. Login work uses synchronous scrypt, suitable for this bounded local installation.

## Wallet protocol

1. Browser calls official SDK `init({timeout:3000})` only on a connect click. Timeout yields a wallet-unavailable state. `getHostNetwork()` must match the server config; older hosts without network context fail closed.
2. `listAccounts()` requests sharing consent, with normalized `NimiqProviderError.is()` handling. The list is never submitted as ownership evidence or used to select a signer. Consensus/block calls use independent settled results; failures show unavailable rather than invented values. Their success is not signature proof.
3. Server validates token, campaign expiry and unused invitation, then creates a five-minute challenge capped at campaign expiry. Unconsumed earlier challenges for that invitation are invalidated. Refreshing the signing request in another tab can therefore invalidate an open prompt; request a new one if that occurs.
4. Server constructs an ASCII JSON message bound to `NimClaim/claim/v1`, request purpose, exact origin, network, immutable campaign/invitation IDs, token hash, exact Luna amount, random 256-bit nonce and expiration. No frontend-chosen address is bound because the wallet chooses its signer. The proof binds the eventual verified signing key to this exact claim request.
5. Browser passes the exact message to `sign(message)` and submits only token, challenge ID, public key and signature. Normalized wallet rejections are ordinary outcomes; original non-wallet/status errors remain distinct. Unknown host error types are retained in diagnostic text.
6. Server retrieves the original stored message, validates invitation/nonce expiry and non-use and checks its origin/network against current configuration. It recreates the official `\x16Nimiq Signed Message:\n` + decimal byte length + message envelope, hashes with SHA-256 and verifies Ed25519 through Nimiq core. Current Nimiq core verifies via `PublicKey.verify(Signature.fromHex(...), digest)`. It derives the address from the verified public key. Raw message signatures, client-supplied messages and claimed addresses are not accepted.
7. In one SQLite write transaction, the server creates a pending claim, consumes its challenge and records the initial history event. Unique constraints prevent multiple claims per invitation/challenge and per wallet/campaign. Failed invalid proofs do not consume the challenge; rate limits and expiry bound retries.
8. A separate authenticated decision transaction changes an unexpired pending claim to payment-ready or rejected exactly once and records its history. No subsequent decision can override it. Campaign expiration transitions pending claims to expired on the next API request, recording the campaign expiry time. Unused links become unusable at the same deadline. Approved unpaid commitments remain payment-ready after campaign expiry.

A network cannot be changed for an existing database. Use a separate database for each network. Signatures attest the network string in the request; message signatures themselves do not prove blockchain network connectivity. Host network context is a client compatibility check; the backend security rests on signature verification of its own domain-bound challenge.

## Endpoint inventory

All paths below are under `/api`. All POST bodies must have `Content-Type: application/json` and `Origin: APP_ORIGIN`.

| Method/path                       | Authority                    | Body / purpose                                                                                 |
| --------------------------------- | ---------------------------- | ---------------------------------------------------------------------------------------------- |
| GET `/config`                     | Public                       | Expected origin and Nimiq network                                                              |
| GET `/session`                    | Cookie                       | Authentication state                                                                           |
| POST `/login`                     | Password                     | `{password}` → session cookie                                                                  |
| POST `/logout`                    | Cookie                       | `{}` → revoke session                                                                          |
| GET `/campaigns`                  | Organiser                    | List campaigns and actual counts                                                               |
| POST `/campaigns`                 | Organiser                    | `{title,description,amount,slots,expires}`; decimal NIM string, integer slots, epoch-ms expiry |
| GET `/campaigns/:id`              | Organiser                    | Campaign, invitation IDs, claims and events; never plaintext invitation tokens                 |
| POST `/campaigns/:id/invitations` | Organiser                    | `{}` → one unique invitation URL, returned once                                                |
| POST `/invitation`                | Invitation token             | `{token}` → campaign and claim/status/history                                                  |
| POST `/challenge`                 | Invitation token             | `{token}` → `{id,message,expires,network}`                                                     |
| POST `/claim`                     | Invitation token + signature | `{token,challengeId,publicKey,signature}` → unique pending claim                               |
| POST `/claims/:id/decision`       | Organiser                    | `{decision:"payment-ready"                                                                     | "rejected"}` |

Errors use `{error:string}`: 400 input, 401 credentials/signature, 403 origin, 404 missing resource, 409 conflict/replay, 410 expiry, 413 oversized body, 415 content type, 429 rate limit. Expiration is evaluated using the server clock. Run hosts with synchronized clocks. Stored timestamps and Luna amounts are integers.

## Native payouts (schema v2)

The payout protocol is documented in [PAYMENTS.md](PAYMENTS.md). All wallet binding, payment review, authorization, reservation, dispatch, outcome reporting and reconciliation APIs require the existing server-side organiser session and exact Origin/JSON checks. Recipient invitation access can read its receipt but cannot initiate or reconcile payments. The local organiser signs; its remote HTLC pays. `senderBindingSupported=false` denotes the absence of an atomic wallet sender guarantee. The separate `htlcVerificationSupported` capability denotes server-side HTLC verification only (SQLite true, PostgreSQL staging false); `enabled` is a configuration gate, not certification of host freshness or release readiness. HTLC type, owner, network-specific trusted cosigner, balance and timeout are independently checked before the challenge and again at reservation. The signed challenge binds both wallet roles and the exact payout. See the payment document for account-cache, native-prompt race and full-node trust limitations.

Additional authenticated POST routes:

| Path                              | Body / purpose                                                                                                                          |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `/campaigns/:id/wallet/challenge` | `{}` → session-bound campaign wallet authorization message                                                                              |
| `/campaigns/:id/wallet`           | `{challengeId,publicKey,signature}` → immutable verified signing wallet                                                                 |
| `/claims/:id/payment/review`      | `{}` → exact payment details and server gate reasons                                                                                    |
| `/claims/:id/payment/challenge`   | `{sender}` → independently verify the candidate HTLC and issue a session-bound exact-intent authorization message                       |
| `/claims/:id/payment/reserve`     | `{challengeId,publicKey,signature}` → immutable intent, durable attempt and one-time permit, only when every backend safety gate passes |
| `/payments/:id/dispatch`          | `{permit}` → atomically consume one-time broadcast authorization                                                                        |
| `/payments/:id/outcome`           | `{outcome:"hash"                                                                                                                        | "cancelled" | "error" | "timeout",hash?}` → uncertain outcome; never client-asserted success |
| `/payments/:id/reconcile`         | `{hash?}` → independently query official RPC and update state, without sending funds                                                    |

Permits are returned once and stored hashed. Immutable intents retain exact approved allocation and recipient. Reservation accepts no posted `state`, `sender`, `amount` or `recipient` overrides; only the challenge route accepts an independently verified HTLC lookup candidate. No candidate hash becomes a paid receipt without backend execution/finality checks. Unknown and failed attempts remain locked and cannot be reset through the API. Hash uniqueness is global. Reconciliation cannot downgrade an already terminal outcome in a concurrent request.

`SPENDING_ENABLED=false` is the default; HTTPS, explicit matching spending network, positive amount limit, independent RPC and a verified Nimiq Pay HTLC are all required. RPC credentials are never returned by `/config`. `HttpRpc` rejects all write methods. Preserve the existing database/credentials; do not use a public tunnel for the private mobile-test setup. Native chain data and receipt addresses are public, and server storage contains both organiser and recipient wallet identifiers.

## Isolated Render + Neon Free staging

`start:staging` enforces HTTPS/TESTNET and the approved isolated Neon database. It accepts only a pooled `DATABASE_URL` for `nimclaim_app`; administrative connection secrets and organiser hashes are rejected in the runtime environment. Startup uses read-only transactions to verify effective role privileges, migration checksums, reviewed schema structure and an existing organiser. It never migrates or bootstraps. Explicit local `staging:migrate` and one-time `staging:bootstrap` commands use a protected direct credential file. Certificate and hostname verification remain mandatory. Missing migrations, schema drift, excess privileges, an absent organiser or an unavailable database prevent listening; there is no SQLite fallback. The ordinary start command refuses Render/Postgres settings. PostgreSQL challenge refresh invalidates previous unused proofs without DELETE. Runtime has no DELETE, DDL, role membership, ownership, native reservation/dispatch or sequence privileges. Its only payment write is INSERT into immutable `manual_payment_receipts`; it cannot update, delete or truncate receipts. Existing financial triggers and permanent UNKNOWN locks remain enforced. Expired sessions and invalidated challenges are retained; any future retention cleanup is an explicit separately reviewed administrative task.

The public gateway permits recipient and login/session/authenticated organiser workflow routes, the single read-only `POST /api/claims/:id/payment/verify` endpoint, and a minimal `/healthz`. It denies native payment reservation, dispatch, broadcast, reconciliation and debug routes. The API independently enforces the same boundaries; there is no Postgres broadcast implementation or bypass flag. `/healthz` is process liveness after successful startup, makes no database query and carries no private data; request-time database failure returns a generic unavailable response.

Security state lives in Postgres: hashed sessions and shared global 10-login/180-other-request minute buckets survive restart, sleep and overlapping processes. Forwarded client IPs are never trusted. Global limits can cause shared throttling under abuse, so this remains a supervised trial, not general production. `SELECT ... FOR UPDATE` locks campaign slot allocation, invitation/challenge consumption and claim decisions; uniqueness constraints arbitrate conflicting wallet claims. History insertion and the state change commit together. Bigint/domain bounds and checked driver parsing prevent silent Luna rounding. Payment identity/history/hash/UNKNOWN-lock constraints are enforced in SQL even though staging cannot initiate payment operations.

The shared HTTP contract preserves exact Origin, JSON/size validation, CSP, HSTS, cookies and static boundaries for both stores. Signature verification continues to use the original server-stored message and Nimiq signed-message envelope. Postgres/driver/backup failures never print SQL values, tokens, signatures, hashes or connection strings. Encrypted backups are operator-controlled, not public routes. See [setup, test evidence and acceptance](RENDER-STAGING.md).
